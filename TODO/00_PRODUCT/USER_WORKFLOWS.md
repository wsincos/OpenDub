# User Workflows

## Workflow A：创作者完成一段视频配音

### 前置条件

- 用户拥有视频、台词和参考声音的合法使用权。
- 已运行 `opendub doctor`，至少一个 Stable 模型可用。

### 操作路径

1. 创建项目，填写项目名和素材来源说明。
2. 导入视频；系统探测格式并生成代理视频、原音轨和封面帧。
3. 导入 SRT/VTT，或手动创建台词片段。
4. 导入参考声音，确认声音授权声明并绑定角色。
5. 选择一个或多个片段，设置情感、强度和模型。
6. 提交生成；系统依次执行视频特征、文本预处理、模型推理、声码器和后处理。
7. 试听候选，查看时长偏差、音色相似度和情感指标。
8. 确认候选；系统生成连续配音轨。
9. 选择保留、降低或移除原音轨，导出 MP4 和 WAV。
10. 导出运行报告，用于复现和申报演示。

### 成功结果

项目目录包含源素材引用、代理文件、片段配置、候选音频、确认音轨、最终视频、指标报告和运行清单。所有输出均可通过项目清单定位。

## Workflow B：研究人员比较模型

1. 复制一个项目为“比较实验”。
2. 固定输入视频、台词、参考音频、目标时间窗和随机种子集合。
3. 选择两个满足所需能力的适配器。
4. 使用 CLI 批量生成所有片段和种子。
5. 运行统一评测器。
6. 导出 CSV/JSON 汇总、单片段报告和运行环境清单。
7. 在报告中引用原模型论文、代码提交和权重校验和。

模型比较只能在共同支持的输入与能力上进行。若某模型不支持情感强度，则相应指标标记为 `not_applicable`，不能自动填充默认值后声称公平比较。

## Workflow C：开发者接入一个新模型

1. 阅读模型适配器协议和许可要求。
2. 创建独立适配器包，声明 `ModelCapabilities`。
3. 实现环境检查、权重解析、输入准备、生成和清理接口。
4. 使用内置合成样本通过契约测试。
5. 使用真实权重通过一个授权样本烟雾测试。
6. 增加模型卡、权重清单、引用和限制说明。
7. 提交 Pull Request；CI 标记为 Experimental。
8. 完成可复现性、指标和安全审核后升级为 Stable。

## Workflow D：维护者发布新版本

1. 冻结范围并检查追踪矩阵。
2. 运行全部自动化测试与真实模型烟雾测试。
3. 生成 SBOM、许可证报告、容器镜像和 Python 包。
4. 在干净 NVIDIA Linux 环境执行快速开始。
5. 录制版本 Demo，更新模型状态表与已知限制。
6. 创建带签名标签和 GitHub Release。
7. 发布权重清单与校验和，不在 Git 仓库存储大权重。
8. 发布后运行安装验证，并在 48 小时内处理阻断问题。

## Workflow E：任务失败后的恢复

1. 任务状态停在失败阶段，不删除已生成的中间产物。
2. UI 显示失败阶段、错误类别和恢复操作。
3. 用户可执行“从失败阶段重试”，无需重复前序分析。
4. 若更换模型或输入，系统创建新的运行记录，不覆盖旧记录。
5. `opendub doctor --report` 生成不包含原始声音和视频的诊断包。

## 状态模型

项目：`draft → ready → generating → review → rendered`。

片段：`unconfigured → ready → queued → analyzing → synthesizing → evaluating → review → accepted`，任一运行阶段可进入 `failed` 或 `cancelled`。

候选：`generated → evaluated → accepted/rejected`。

所有状态转换由核心领域服务控制，Web UI 不得直接修改持久化状态。
