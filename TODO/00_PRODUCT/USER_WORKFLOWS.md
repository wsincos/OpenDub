# OpenDub User Workflows

## Workflow A: A reviewer understands the platform

1. Open `/explore`.
2. Inspect Video, Target Text, and Authorized Reference Speech on a shared time axis.
3. See that a complete method produces target speech, while OpenDub muxes that speech into a dubbed video.
4. Open `/methods` and see the three-method research progression.
5. Visit Evidence Room to verify that method availability and product claims are evidence-bound.

**Success:** the reviewer can state both the AIGC application value and the fact that OpenDub is not an unverified hybrid model.

## Workflow B: A creator chooses a complete method

1. Start with a concrete need: visual prosody, multi-scale speaking style, or explicit emotion control.
2. Use the capability comparison and method cards to narrow to HPMDubbing, StyleDubber, or EmoDubber.
3. Open the Method Canvas and inspect required inputs, optional controls, expected output, limitations, and runtime status.
4. Choose `Prepare project`.
5. The selected complete method and its declared requirements are copied into a local project draft.

**Success:** the user makes an informed method choice without being told that the chosen method is globally best or already Live.

## Workflow C: A creator prepares an authorized local project

1. In Studio, create a project and add owned or authorized video.
2. Add target text, an authorized reference-speech asset, a rights record, and a time window.
3. Review the selected method's input contract and any unavailable runtime prerequisite.
4. Save the project revision and export its manifest when collaborating with a researcher or method owner.

**Success:** preparation is useful even when Live execution is disabled; no source voice is treated as authorized by default.

## Workflow D: A student investigates one method interactively

1. Select one method from `/methods`.
2. Follow the complete graph from multimodal inputs to target speech.
3. Click a component and read its purpose, inputs, outputs, source, and the signal type that can be observed.
4. Use the method-specific lens: HPM hierarchy, Style multi-scale alignment, or Emo emotion guidance.
5. Read the `Concept` label and understand that the view explains a mechanism rather than generating fresh audio.

**Success:** the viewer can describe the method's distinctive contribution without confusing it with another method.

## Workflow E: A developer contributes a complete method

1. Read the complete-method admission contract and create a Method Manifest.
2. Provide paper/source evidence, input/output contract, capability declarations, component graph, status, and license records.
3. Validate the manifest locally.
4. Optionally provide an authorized Replay bundle or an isolated complete-method Adapter.
5. Submit the method for source, rights, and content review.

**Success:** a new complete method can extend the platform without changing the existing three methods or inventing a common hybrid model.

## Workflow F: A verified result is inspected or compared

1. A user opens a qualified Replay or Live result tied to a project and selected method.
2. The result shows source, input hashes, rights, status, and any genuine registered signals.
3. Comparison unlocks only when at least two results share the same video, text, reference-speech, timing, and preprocessing records.
4. The user can listen, inspect metrics that are applicable, and export a bounded comparison report.

**Success:** no result is ranked or called comparable merely because it looks similar.
